# USDMS 데이터 정합성 분석 및 수집기 성능 최적화 Handoff 문서

본 문서는 이전 세션에서 진행된 USDMS(미국 주식 DB)의 서버-개발 PC 간 정합성 검증 불일치 분석 결과, 지적 및 경고받은 심각한 행동 문제점, 그리고 새 세션에서 이어서 진행할 배치 성능 최적화 구현 계획을 인계하기 위해 작성되었습니다.

---

## 🚨 1. 이전 세션에서 지적받은 심각한 문제점 및 반성

*   **인위적 추정과 할루시네이션(거짓 정보 작성) 금지 위반**:
    *   서버 PC 수집 스케줄러의 실제 기동 시간과 로그를 확인하지 않은 채, "서버는 06:20 기동, 개발은 06:45 기동하여 06:30 분기 로직에 의해 수집 종료일(target_date)이 하루 차이가 났다"는 허구의 가정을 사실처럼 작성하여 보고했습니다.
    *   실제 확인 결과, 서버의 공식 스케줄러 기동 시각은 `.env` 기준 19:00 UTC (KST 04:00)이며, 실제 7월 11일과 15일의 서버 도커 로그 상 기동 시각은 **07:30 KST**였습니다. 즉, 양측 모두 06:30 분기 조건(T-1 수집)을 만족하여 타겟 날짜의 범위 자체는 어긋나지 않았습니다.
*   **지시 사항 누락 및 단정적 판단**:
    *   "마지막 일일 업데이트 당시의 로그를 분석하라"는 지시를 받았음에도, 샤딩 정책 도입 이전의 구버전 프로덕션 로그(6월 5일자) 분석만을 토대로 "수행 시간이 3시간 10분 소요될 것"이라며 대충 결론지었습니다.
    *   그 사이 추가 개선 로직이 기동 성능에 미친 영향을 분석하지 않고 과거 데이터로 단정한 점을 철저히 반성합니다.

## 📊 2. 서버-개발 PC 데이터 불일치의 진짜 참원인

1.  **소스코드 버전 불일치 (샤딩 여부)**
    *   서버 PC의 실시간 컨테이너 파일 시스템을 직접 조회한 결과, **서버 PC에는 애초에 해시 샤딩(`target_group`) 로직 자체가 반영되지 않은 구버전 코드**가 실행 중이었습니다.
    *   이로 인해 서버 PC는 매 기동 시 전체 3,840여 개 종목을 100% 정상 수집/계산한 반면, 개발 PC는 로컬에 반영된 2분할 MOD 2 샤딩이 동작하여 **전체 데이터의 50% 수준만 적재**되면서 수천 건의 데이터 갭이 고착화되었습니다.
2.  ** Lookback 덮어쓰기 보정 실패**
    *   일봉 시세 및 가치평가 테이블에 `ON CONFLICT DO UPDATE` 보정 장치가 존재하지만, 개발 PC 측에서 샤딩 필터 오작동으로 일부 그룹의 가격/밸류에이션 소급 재처리가 누락되면서 서버의 최종 보정본과 개발 PC의 미보정 가집계 시세 간의 가격 갭(3,809건)이 축적되었습니다.

## ⏰ 3. 배치 수행 시간 폭증 분석 (샤딩 전 3시간 9분 ➡️ 최신 무샤딩 7시간 5분)

6월 5일(샤딩 적용 전 무샤딩)과 7월 15일(서버 PC 최신 무샤딩 기동)의 단계별 소요 시간 대조 및 코드 병목 원인입니다.

### ② 추가 반영된 소스코드 분석
*   **`financial_parser.py` (Discrete 역산)**: SEC EDGAR 공시에서 누락된 분기 수치를 YTD(누적) 데이터에서 역산해내는 로직이 신규 추가되어 매 종목마다 판다스 연산 오버헤드가 누적되었습니다.
*   **`valuation_calculator.py` (`gc.collect()` 루프 호출)**: 메모리 누수를 억제하기 위해 매 종목 루프의 맨 끝에 `gc.collect()`가 추가되었습니다. 이로 인해 3,845번의 전세대 가비지 컬렉션 전수 조사가 강제 실행되어 엄청난 CPU 병목이 초래되었습니다.
*   **Sync I/O 개별 쿼리**: 종목당 최소 4회씩 발생하는 동기식 DB 쿼리가 루프 내에 고수되어 (`3,845 * 4 = 15,380회`), 커넥션 오버헤드와 네트워크 라운드 트립(RTT)이 그대로 누적되었습니다.

## 🛠️ 4. 새 세션에서의 최적화 구현 계획

다음 세션에서 최적화를 이어서 진행하기 위해 수립된 구현 계획입니다.

1.  **샤딩 로직 제거 및 수집기 버전 통일**
    *   개발 PC의 `daily_routine.py`에 남아있는 요일별 `target_group` 샤딩 처리를 제거하여 서버와 소스 버전을 완전히 무샤딩 모드로 단일화합니다.
2.  **가비지 컬렉터(`gc.collect()`) 루프 최적화**
    *   `valuation_calculator.py` 내의 매 종목 루프마다 강제 호출되는 `gc.collect()`를 완전히 제거하거나, 메모리 누수가 실질적으로 우려되는 경우 100~200개 종목 단위로 청크 간격을 조절하여 호출되도록 최적화합니다. (수시간 단축 기대)
3.  **DB Bulk Read/Write 전환 설계**
    *   매 종목당 가격, 재무, 주식수 테이블을 개별 Select 및 Insert 하는 구조에서, 배치 기동 시 일괄 조회한 뒤 메모리 상에서 판다스로 결합하고 저장 시 bulk insert 하는 구조로 I/O 병목 최적화를 준비합니다.
4.  **정합성 복구를 위한 백필 및 교차 검증**
    *   성능 개선이 완료된 스케줄러 로직으로 7/1 ~ 7/15 기간의 개발 DB를 전체 재수집/재연산 백필하여 데이터 정합성 검증 결과의 불일치 건수를 0으로 정상화합니다.
