# 신규 기능 추가 시 시행착오 방지 및 개발 표준 가이드

본 문서는 TDMS 프로젝트 전반과 KDMS(한국 수집기) 모듈에 신규 데이터 수집 기능, API, UI 구성요소를 추가할 때 발생할 수 있는 시행착오를 방지하고 작업 효율성을 극대화하기 위한 종합 개발 가이드라인입니다.

---

## 1. TDMS 프로젝트 전반의 핵심 설계 원칙

### 1) perfect Isolation(개발 환경 격리) 정책 준수
*   **WSL 2 (Ubuntu) 개발 환경이 기본 탑재 디포르트**입니다. 모든 AI/ML, 데이터 과학, 백엔드 수집기(p2_kdms, p3_usdms) 및 도커 기동 등은 WSL 2 터미널(zsh, Miniforge/Conda) 환경에서만 작동해야 합니다.
*   **하지 말아야 할 사항**:
    *   WSL 환경에서 개발 중이면서 `/mnt/c/Users/...` 처럼 윈도우 마운트 파일시스템을 소스 디렉토리로 사용하지 마십시오. I/O 성능 하락 및 권한 꼬임 현상이 발생합니다.
    *   윈도우 네이티브 쉘(PowerShell)의 가상환경 인터프리터와 WSL 내 Conda 인터프리터를 혼용 호출하지 마십시오.

### 2) 민감 정보(Secrets) 하드코딩 엄금
*   API Key, DB 비밀번호, 한투 보안 토큰 정보 등은 소스 코드나 터미널 명령어 인자에 직접 기재하는 것을 영구 배제합니다.
*   **올바른 프로세스**:
    *   `.env` 또는 `.env.template` 에 변수명을 정의하고, `Settings` 객체나 `DatabaseManager` 등 환경 변수 연동 모듈을 통해서만 메모리로 로드하십시오.
    *   git-secrets 보안 도구가 작동하고 있으므로 노출 시 빌드 및 푸시가 차단됩니다.

## 2. KDMS 신규 수집 기능 추가 시의 작업 계획 & 고려사항

### 1) 수집 스케줄러 및 파이프라인 연계
*   신규 데이터 테이블과 수집기가 개발되면, 반드시 `daily_task.py` 파이프라인 내 `DailyTask.run` 의 특정 수집 페이즈(Phase)에 체계적으로 등록해야 합니다.
*   영업일 검증(`is_trading_day`), 당일 수집 대상 종목 필터링(`get_active_symbols_for_date`) 등 기존 공통 모듈을 재사용하여 일관성을 지키십시오.

### 2) 모니터링 로깅 규격화 (tqdm 스타일 진행 모니터링 로그)
대량 종목을 루프 돌며 순차 수집하는 성격상, 로그 창만 보고도 진행 상황을 정확히 유추할 수 있어야 합니다. 다음과 같은 tqdm 스타일 로그 출력을 적용하십시오.
*   **필수 포함 정보**: 진행률 (%), 처리 완료된 아이템 수 / 총 아이템 수, 초당 처리 속도 (it/s), 경과 시간, 예상 남은 시간 (ETA), 현재 처리 중인 티커(종목코드).
*   **출력 예시**:
    ```text
    [수급 수집 진행] 45.2% | 1020/2256 | 8.5 items/s | Elapsed: 00:02:00 | ETA: 00:02:25 | Current Ticker: 005930
    ```

## 3. KIS API 엑셀 스펙 시트(.xlsx) 오류 없는 파싱 및 정보 확보 가이드

한국투자증권 API 개발 가이드에서 제공하는 `.xlsx` 정의서 파일은 컬럼 수가 방대하고 셀 병합이 잦아 수동 파싱 시 오타와 필드 누락이 빈번히 발생합니다.

### 1) 엑셀 로드 및 파싱 안전 규칙
*   **시트 지정 및 헤더 라인 스킵**: `pd.read_excel` 호출 시, 상단의 정보용 병합 행들을 무시하도록 `header=None` 또는 `skiprows=N` 옵션을 명시적으로 지정하여 헤더 레이아웃을 정확하게 타게팅하십시오.
*   **영문-한글 매핑 딕셔너리 구성**:
    *   영문 파라미터명과 DB 컬럼 매핑의 정합성을 수립하기 위해 엑셀 내 영문명 열과 한글 설명 열을 1:1 dictionary 구조로 정의하여 바인딩 실수를 방지하십시오.
    *   문자열의 앞뒤 공백으로 인해 매핑이 누락되지 않도록 `.strip()` 을 필수 적용하십시오.

### 2) 타입 캐스팅 및 Null 방어 처리
*   KIS API 응답 JSON의 수치 필드들은 대다수 큰따옴표가 포함된 문자열(`"15797656"`)로 반환됩니다.
*   **올바른 처리**:
    *   DB 스키마 타입에 맞춰 정밀하게 형변환(`int()`, `float()`)을 진행하되, 공백(`""` 또는 `"-"`)이나 Null 값이 넘어오는 경우 `0` 또는 `None`으로 안전하게 치환(Fallback)하는 방어 로직을 작성하십시오.
    *   형변환 실패 시 크래시(Crash)가 나지 않도록 유틸리티 변환 함수(`to_int`, `to_float`)를 거치도록 하십시오.

## 4. 도커 이미지 빌드 및 컨테이너 가동 정책

### ⚠️ 절대 하지 말아야 할 실수 (실패 사례)
*   **소스 코드 수정 후 그냥 restart/up 실행**:
    *   TDMS 코어 컨테이너(p2_kdms, p3_usdms 등)는 로컬 디렉토리의 소스를 바인딩 볼륨 마운트하여 실시간 참조하지 않고, 빌드 타임에 이미지 내부로 복사(`COPY`)하는 아키텍처입니다.
    *   소스 코드를 수정하고 단순히 `docker compose restart` 또는 단순히 `docker compose up`만 치면 변경사항이 반영되지 않고 **구버전 바이너리가 돌아가서 변경점이 미반영되는 참사**가 납니다.

###  올바른 가동 프로토콜
*   백엔드 코드를 수정한 후에는 **반드시 `--build` 옵션을 강제**하여 이미지를 재구성하십시오.
    ```bash
    docker compose up -d --build p2_kdms
    ```
*   도커 컴포즈 빌드가 백그라운드로 성공적으로 마쳐졌는지 `docker compose ps` 및 로그(`docker compose logs -f p2_kdms`)를 통해 확인하십시오.

## 5. UI 변경 검증 및 피드백 획득 프로세스 가이드

프론트엔드 UI 화면의 변경을 검증할 때 개발 에이전트가 자의적으로 브라우저 도구를 켜서 확인을 자체 종결하지 않도록 합니다.

###  올바른 프론트엔드 검증 절차
1.  **자동화 테스트 우선 실행**:
    *   변경 사양이 UI 상태(Store)나 컴포넌트 렌더링에 미치는 영향은 `vitest` 유닛 테스트를 통해 논리적으로 검증합니다.
2.  **도커 배포 반영 및 사용자 점검 환경 확보**:
    *   수정 내용이 웹 서비스 화면에 완전히 노출되어 사용자가 직접 눈으로 보고 테스트할 수 있도록, 소스가 변경된 도커 이미지를 재빌드(`--build`)하고 컨테이너를 업(up) 완료 상태로 유지합니다. (별도 신규 독립 테스트 서버를 기동하거나 인프라를 구축하라는 의미가 아님)
3.  **기존 규칙 및 구현 방식 현행 검토**:
    *   신규 데이터 테이블이나 컴포넌트를 UI에 맵핑할 때, 기존 소스에 정의된 입력 규칙, UI 폼 바인딩 구조 및 디폴트 규칙을 사전 분석하십시오. 
    *   그 규칙과 일치하도록 반영하는 것으로 충분하며, 이후 화면 사용에 불필요한 기본값 하드코딩이나 임시 테스트성 오버라이딩 필터값을 남겨두어 실사용에 불편을 유발하지 않도록 각별히 유의하십시오.
4.  **점검 준비 안내 및 피드백 획득**:
    *   사용자가 접속해 즉시 점검할 수 있는 접속 경로(예: `http://localhost:3000/explorer` 등)를 안내하고 피드백을 요청합니다.
