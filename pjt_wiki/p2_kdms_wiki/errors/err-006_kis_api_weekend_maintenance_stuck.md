# [P2-ERR-006] KIS API 주말 점검으로 인한 수집 스레드 정체(Stuck) 장애

> **Sub Project**: p2_kdms
> **Severity**: High
> **Date**: 2026-07-04
> **관련**: `[[p2_kdms_wiki/interfaces/financial_repo.md]]`, `[[p2_kdms_wiki/decisions/dec-007_financial_update_optimization.md]]`

---

## 1. 증상

* 토요일 오후 서버 PC의 재무수집이 개시된 지 1시간 30분이 지난 시점까지 로그 스트림 출력이 정체(Stuck) 상태로 유지되었습니다.
* CPU 점유율은 미미하나 수집 프로세스가 다음 단계로 넘어가지 않고 행업 현상이 관찰되었습니다.

---

## 2. 원인 분석

1. **KIS OpenAPI 서버 주말 정기 점검**: 토요일 오후 KIS OpenAPI 서버(`openapi.koreainvestment.com:9443`) 점검에 따라 접속이 원천 차단(`Connection refused`)되었습니다.
2. **지연 시간의 선형적 누적**:
   * 재무제표 7종 API를 순차 호출하는 과정에서 각 API 접속 실패 시마다 지수 백오프 재시도 딜레이(2초, 4초, 8초 = 총 14초)가 발생합니다.
   * 종목당 최대 98초 딜레이가 순차 누적되어, 3,911개 종목에 대한 루프를 도는 과정에서 사실상 수집 스레드가 무한 정체(Stuck)되었습니다.

---

## 3. 해결책 및 조치 내역

1. **컨테이너 restart 조치**:
   * 사용자의 승인을 얻어 서버 PC의 `p2_kdms` 컨테이너를 강제 재시작(`docker restart p2_kdms`)함으로써 교착 상태에 빠진 수집 스레드를 정상적으로 강제 종료 및 복구하였습니다.
2. **사후 대책**:
   * 본 세션에서 도입된 **일일 쿼터 샤딩(600개 제한)** 및 **인메모리 캐싱** 기법을 통해 순회 대상을 대폭 필터링하여 이러한 점검 시간대와 맞물렸을 때의 오동작 여파를 최소화하였습니다.
   * 네트워크 차단이 감지될 경우 수집 루프 자체를 탈출(Break)하여 전체 스레드가 묶이지 않도록 예외 처리 설계를 향후 수집 태스크 스펙에 적극 반영하도록 지침을 수립했습니다.
