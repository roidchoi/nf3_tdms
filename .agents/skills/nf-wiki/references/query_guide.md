# Query Mode Guide — nf-wiki 조회 모드 상세 프로토콜

> **버전**: v1.0 (2026-05-27)
> **역할**: `nf-wiki` 스킬의 [조회 모드] 전용 운영 가이드.
> 조회 모드 진입 시 이 파일을 읽고 프로토콜을 따르십시오.

---

## 1. 조회 모드란?

사용자 또는 구현 에이전트가 코드 구현·디버깅·설계 과정 중 프로젝트 관련 기술 정보를 확인하고자 할 때, `pjt_wiki`에서 해당 정보를 신속하고 정확하게 찾아 제공하는 기능입니다.

**핵심 원칙**: 위키에 있는 정보라면 독립적으로 추론하거나 인터넷을 먼저 검색하지 말고, **위키를 먼저 조회**하여 프로젝트 특화 컨텍스트를 우선 제공하십시오.

---

## 2. 트리거 판단 기준

### ✅ 조회 모드 트리거 (Should Trigger)

| 케이스 유형 | 예시 |
|---|---|
| 에러 해결 이력 조회 | "KIS API 인증 에러 어떻게 해결했지?", "pg_restore 오류 기록 있어?" |
| 인터페이스/시그니처 확인 | "OhlcvRepo insert 파라미터가 뭐야?", "FinancialRepo 어떻게 써?" |
| 환경/패키지 확인 | "p2 conda 환경 이름이 뭐야?", "psycopg2 버전 확인해줘" |
| 아키텍처/의사결정 확인 | "PIT 패턴 왜 이렇게 설계했지?", "수정주가 전략이 어떻게 되지?" |
| 구현 전 사전 조회 | "기존에 이런 기능 구현된 거 있어?", "이 모듈 구조가 어떻게 돼?" |
| 에이전트 자체 판단 | 코드 작성 전 기존 인터페이스 확인이 필요하다고 판단될 때 |

### ❌ 비트리거 케이스 (Should NOT Trigger)

| 케이스 유형 | 예시 |
|---|---|
| 위키 작성/업데이트 요청 | "위키 업데이트해줘", "이 내용 위키에 추가해줘" |
| 외부 라이브러리 일반 질문 | "FastAPI 라우터 어떻게 만들어?", "psycopg2 사용법 알려줘" |
| 코드 구현 직접 요청 | "이 함수 구현해줘", "T-XXX 작업 시작해줘" |
| 위키와 무관한 시스템 설정 | "WSL IP 주소 확인하는 법", "conda 설치 방법" |

## 3. 위키 파일 라우팅 맵

MoC(`index.md`) 탐색 전 질문 키워드로 우선 탐색 경로를 빠르게 좁힙니다.

| 질문 키워드 유형 | 우선 탐색 경로 |
|---|---|
| 에러, 버그, 오류, 해결, 트러블슈팅 | `p{n}_wiki/errors/` |
| API, 함수, 시그니처, 인터페이스, Repo, 클래스 | `p{n}_wiki/interfaces/` |
| 환경, Conda, 패키지, .env, 버전, 설치 | `p{n}_wiki/environment.md` |
| 폴더 구조, 모듈, 코드베이스, 파일 위치 | `p{n}_wiki/codebase_map.md` |
| 의사결정, 왜, 설계 이유, ADR, 채택 | `p{n}_wiki/decisions/` |
| 배포, 실행 명령, Runbook, ops | `p{n}_wiki/operations/runbook.md` |
| 공통 정책, 전체 아키텍처 | `parent_wiki/` |
| 전체 현황, 진행도, 어디 있는지 모름 | `00_schema/index.md` |

> **p{n} 판단 기준**: 질문에서 p1(공유 인프라) / p2(KDMS, 한국) / p3(USDMS, 미국) / p4(Manager) 중 특정되면 해당 위키 우선. 불명확하면 `index.md`에서 판단.

---

## 4. 조회 절차 상세

### STEP 1 — MoC 탐색

`00_schema/index.md`를 읽고:
- 질문과 관련된 서브 위키(p1~p4, parent) 특정
- 해당 위키 내 관련 파일 경로 식별
- 파일 특정 가능 → STEP 2 직행
- 파일 불명확 → `grep_search` 보조 탐색

### STEP 2 — 핀포인트 읽기

- 특정된 파일을 직접 읽습니다 (**최대 3개 파일 상한** 준수).
- `grep_search` 보조 탐색 시:
  - `SearchPath`: `pjt_wiki/`
  - `Query`: 질문의 핵심 식별자 (함수명, 에러 코드, 모듈명, 환경 변수명 등)
  - 결과에서 가장 관련도 높은 파일 1~2개만 읽기

### STEP 3 — 답변 생성

아래 **상황별 포맷 규칙(§5)** 에 따라 답변을 구성합니다.

### STEP 4 — 갱신 제안 (조건부)

- 위키에 정보 없음: *"해당 정보가 위키에 없습니다. 해결 후 [업데이트 모드]로 추가하시겠습니까?"*
- 정보가 있으나 오래된 듯: *"위키 항목이 오래된 것 같습니다. 업데이트가 필요하면 알려주세요."*

---

## 5. 상황별 답변 포맷 규칙

상황에 맞는 포맷을 선택하십시오. 획일적으로 한 가지 포맷을 강요하지 않습니다.

### 포맷 A — 단답형
**언제**: 함수 시그니처 한 줄, 환경 이름, 패키지 버전 등 간단한 사실 확인

```
{요청한 정보}
📁 출처: `{파일 경로}`
```

### 포맷 B — 발췌형 (기본 권장)
**언제**: 에러 해결법, 인터페이스 명세, 의사결정 배경 등 맥락이 필요한 정보

```markdown
## 📚 위키 조회 결과

**출처**: `{파일 경로}`

{원문 핵심 내용 발췌 — 코드 블록, 표, 목록 등 원문 포맷 유지}

📁 **관련 파일**: [{파일명}](file://{경로})
```

### 포맷 C — 요약 테이블형
**언제**: 에이전트가 구현 전 사전 조회하거나, 여러 파일에 걸친 복합 조회

```markdown
## 📚 위키 조회 요약

| 항목 | 핵심 내용 | 출처 |
|---|---|---|
| {항목1} | {내용} | `{파일}` |
| {항목2} | {내용} | `{파일}` |

> 💡 구현 시 주의: {위키에서 발견한 주의점}
```

---

## 6. 위키에 답이 없을 때

1. **솔직하게 보고**: "pjt_wiki에서 해당 정보를 찾지 못했습니다."
2. **대안 탐색 시도**: 코드베이스 직접 grep 또는 일반 지식으로 보조 답변 제공
3. **업데이트 제안**: 정보를 확인한 후 위키 등록을 권유

---

## 7. 에이전트 자체 조회 패턴 (구현 전 체크리스트)

에이전트가 코드 구현을 시작하기 전, 아래 항목을 자동으로 조회하십시오:

1. **인터페이스 확인**: 호출할 Repo/클래스의 시그니처가 `interfaces/`에 있는가?
2. **에러 이력 확인**: 유사한 작업에서 발생한 에러 기록이 `errors/`에 있는가?
3. **환경 확인**: 사용할 Conda 환경, 패키지 버전이 `environment.md`에 있는가?
4. **의사결정 확인**: 이 작업과 관련된 기존 ADR이 `decisions/`에 있는가?

이 체크리스트를 거치면 위키에 이미 기록된 함정(에러, 설계 제약)을 재발하지 않을 수 있습니다.
