## 배경

1. **지나치게 긴 실행 시간**: 매일 KIS API를 통해 전체 Active 종목(3,911개)에 대한 재무 정보를 조회할 경우, 종목당 7종의 API를 호출하여 총 27,000회 이상 호출(동기식)이 일어나고, 수집 완료에 1시간 이상 소요되었습니다.
2. **N+1 SQL 병목**: 수집 루프 내에서 각 종목의 결산년월(yymm) 마다 개별적으로 DB 조회를 날리던 구조로 인해 DB 커넥션 부하 및 디스크 병목이 발생했습니다.
3. **재무 정보 특성**: 상장사의 재무제표는 분기별 공시 이벤트 시점에만 변하므로, 평일에 매일 전체 종목을 강박적으로 전수 갱신할 필요가 없습니다.

---

## 결정 내용

### 1. 결정론적 해시 기반 요일별 5분할 순환(Deterministic Hash Sharding) 도입
* **배경**: 기존의 수집 시각(`retrieved_at`) 기준 하위 600개 샤딩 방식은 수집 실패 종목(장애 또는 공시 미보고 등)의 수집 시각이 과거로 남아 매일 600개 슬롯을 잠식하는 '블랙홀 현상'을 유발할 수 있습니다.
* **해결**: 전체 활성 상장 종목에 대해 결정론적 해시 알고리즘(`MD5` MOD 5)을 적용해 0(월)~4(금) 그룹으로 고정 분할하고, 주중(월~금) 해당 요일의 그룹에 매핑되는 종목들만 타겟으로 선정하여 일일 수집을 진행합니다.
* **기대효과**: 
  - 각 요일별로 고르게 약 550~600여개 종목이 배정되어 일일 API 쿼터 한도를 충족합니다.
  - 특정 종목 수집 실패가 다른 요일의 수집 흐름에 영향을 끼치지 않아 병목이 원천 예방됩니다.
  - 매주 규칙적으로 재조회가 수행되므로, 수정 공시가 발생하더라도 최대 1주일 내로 완벽히 정합성이 동기화됩니다.

### 2. 수동 기동 시 전 종목 실행 옵션 연동
* 스케줄러 자동 실행 시에는 요일별 5분할 수집을 따르되, 사용자의 수동 API 트리거 시에는 분할 필터링을 거치지 않고 전체 활성 종목을 수집할 수 있도록 `target_group=-1` 파라미터를 추가하여 제어합니다.

### 3. DB N+1 SELECT 제거 및 인메모리 벌크 캐싱 적용
* 루프 내 개별 DB SELECT를 차단하고, 시작 시 대상 종목들의 최신 수집 정보를 **단 1회** 벌크 쿼리(`get_latest_statements_bulk`, `get_latest_ratios_bulk`)로 사전 적재해 메모리에서 비교합니다.
* 루프 내부에서는 메모리 캐시 대조를 통해 실제 변경분이 감지된 레코드만 메모리 버퍼에 담은 뒤, 루프 외부에서 **일괄 벌크 저장**(`insert_statements`, `insert_ratios`)합니다.
