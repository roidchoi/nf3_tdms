# TDMS 유지보수 및 문제 해결 세션 초기 지침 (주입용)

본 문서는 기존 TDMS 프로젝트의 버그 수정, 성능 고도화, 추가 기능 구현 및 유지보수 세션이 기동되었을 때, 에이전트가 작업 시작 즉시 초기 지침으로 자동 주입받아 준수해야 하는 행동 강령이자 작업 위생 지침입니다.

---

## Part 1. 세션 시작 즉시: 사실 기반 진단 및 맥락 동기화 (Catch-up)

에이전트는 사용자가 버그 제보, 수정 요청, 또는 기능 고도화를 지시하며 세션을 시작할 때, 독단적인 추정이나 코딩을 전면 보류하고 아래 절차에 따라 철저한 팩트 체크와 위키 조회를 수행해야 한다.

### 1-1. 사실 기반 현상 분석 및 할루시네이션 원천 배제
* **추정/짐작 답변 영구 금지**: 명확한 물리적 증거(데이터) 검증 없이 자의적으로 "API 장애인 것 같습니다" 또는 "캐시가 꼬인 것 같습니다"와 같이 추정하거나 예측하여 없는 사실을 지어내어 보고하는 행위를 절대 금지한다.
* **객관적 팩트(Fact) 수집 의무**: 오직 실제 로그 파일 내용, 캐시 JSON 구조, 데이터베이스 쿼리 결과, 소스 코드의 실제 변수/임포트 선언 상태를 도구(`view_file`, `grep_search`, `run_command` 등)로 직접 확인하고 검증 완료한 수치와 팩트만을 기반으로 상황을 분석하고 사용자에게 설명해야 한다.
* **불확실성 인정**: 로그나 코드로 확인되지 않는 영역은 솔직히 한계를 밝히며, 아는 척 설명하지 않고 필요시 사용자에게 직접 확인 또는 데이터 제공을 정중히 요청한다.

### 1-2. Wiki 지식을 통한 프로젝트 맥락 파악 및 동기화
* **Wiki 선조회 의무화**: 코드를 수정하거나 고도화 계획을 짜기 전에, 반드시 `nf-wiki` 스킬을 사용하여 `pjt_wiki`와 각 서브프로젝트의 wiki 폴더를 조회한다.
* **중점 파악 항목**:
  - `decisions/` 디렉토리: 이미 합의된 아키텍처 결정 사항 및 명명 규칙 확인.
  - `errors/` 디렉토리: 유사 구현이나 과거 세션에서 발생했던 동일/유사 에러와 기존 해결 지식 파악.
  - `interfaces/` 디렉토리: 연동 대상 API 스펙 및 데이터베이스 스키마 형태 확인.
* **맥락 일치**: 파악한 위키 지식을 기반으로 프로젝트 도메인 맥락과 완벽하게 정렬된 상태에서만 작업을 진행하며, 이미 결정된 설계 방향과 모순되는 코드를 작성하지 않는다.

### 1-3. 에러 로그 및 최근 변경점 추적
* **동작 중인 컨테이너 로그 수집**: 오류 발생 시 `docker compose logs --tail=100 <서비스명>` 또는 `/logs/` 하위의 실제 로그 파일(예: `daily_update.log`)을 읽어 크래시 시점의 정확한 Stacktrace와 에러 메시지를 수집한다.
* **상태 캐시 데이터 백업 및 확인**: `task_status_cache.json` 등의 상태 보존 파일에서 태스크의 마지막 동작 정보(성공/실패 수치, 현재 진행 Phase 등)를 읽어 문제 상황과 대조한다.
* **최근 소스 변경점(Git) 추적**: `git diff` 또는 `git log -n 5` 등을 활용하여 최근에 수정된 영역과 이력을 파악한다.

## Part 2. 코드 수정 위생: 부작용 최소화 및 정밀 타격 (Hygiene)

기존에 잘 돌고 있는 프로덕션 환경의 코드를 건드릴 때 발생하는 런타임 오류와 회귀 버그를 방지한다.

### 2-1. 외과적 수정(Surgical Edit) 및 사족 리팩토링 금지
* 사용자가 지시한 오류 지점 또는 기능 추가 지점만 정확하게 타격하여 정밀 수정(외과적 수정)한다.
* 지시받지 않은 주변 로직의 대대적인 구조 변경이나 자의적인 리팩토링은 절대 독단적으로 진행하지 않는다.

### 2-2. 파이썬 임포트/스코프 무결성 보장
* 수정을 마친 후에는 사용된 모든 표준 라이브러리(`os`, `sys`, `time` 등)와 커스텀 유틸리티 클래스(`EnvDetector` 등)가 해당 파일 상단 및 로컬 스코프 내에 누락 없이 임포트되어 있는지 **눈으로 더블 체크**한다.
* 가상환경에서 `PYTHONPATH`를 지정하여 `pytest` 단위 테스트를 로컬로 실행함으로써 신규 참조 에러를 사전 차단한다.
  ```bash
  conda run -n tdms_p2_env env PYTHONPATH=tdms_core/p2_kdms pytest tdms_core/p2_kdms/tests/ -v
  ```

### 2-3. 캐시 저장 격리성 확보 (State Persistence Safety)
* `FilePersistentDict` 등 상태 객체를 업데이트할 때는 내부 서브 딕셔너리의 미세한 변경이 직렬화 누락을 유발하지 않도록 `dict(job_statuses.get(job_id))` 형태로 얕은 복사본을 생성해 재할당한다.
  ```python
  status_dict = dict(job_statuses.get(job_id, {}))
  status_dict.update({ "steps": steps, "last_log": log_msg })
  job_statuses[job_id] = status_dict # 재할당을 통해 물리 파일 쓰기(_save) 강제 트리거
  ```

## Part 3. 사용자 관점의 소통 및 요구사항 물리적 일치 (UI/Wording)

에이전트가 화면 문구를 자의적으로 멋대로 해석하거나 쓸데없는 설명조의 텍스트를 추가하여 사용자의 인내심을 시험하는 일을 원천 방지한다.

### 3-1. 자의적 UI 해석 금지 및 극단적 간결화
* "간결하게 하라"는 지시는 한글 서술형 문장을 배제하고 정량적인 통계 수치만을 파이프라인(`|`) 기호로 명료하게 조합하라는 뜻이다.
* **단어 중복 절대 금지**: 상단 타이틀이나 카드 제목에 명시된 단계명(예: `Daily OHLCV Backfill`)을 하위 설명 영역에 구구절절 반복 서술하지 않는다.
* **출력 템늘릿 선제 검증**: 코드에 직접 문구를 작성하기 전, 사용자에게 반영할 문구 템플릿 예시(텍스트 포맷)를 먼저 보여주고 "이 형태로 통일해서 노출하겠습니다"라고 합의한 뒤 구현한다.
  * *좋은 예*: `성공: 513건 | 실패: 1건 | 수집: 12321건` (한 줄 배치, 줄바꿈 없음)
  * *나쁜 예*: `일봉 백필 성공적으로 완료되었습니다. 성공 513종목 수집 완료...` (서술형, 장황함)

### 3-2. 캐시 데이터 기반 UI 일치 (No Guessing)
* 대시보드 UI에 통계나 수치를 뿌려줄 때는 로그 텍스트 정규식 매칭에만 기대지 말고, 상태 캐시에 기록된 정량 데이터 구조(예: `steps`)를 우선 바인딩한다.
* 캐시가 없는 과거 로그 등 fallback 상황에서만 안전한 예외 처리를 거쳐 로그 파싱을 수행하되, 실패 건수가 불일치 건수로 잘못 호도되지 않도록 안전장치를 둔다.

## Part 4. 배포 프로토콜 및 피드백 획득 (Deployment & Feedback)

### 4-1. 빌드 타임 반영 강제 (`--build` 옵션 필수)
* TDMS의 도커 컴포즈 구조상 로컬 소스 파일 수정 시 볼륨 바인딩 실시간 참조가 차단될 수 있으므로, **모든 백엔드/매니저 코드 반영 시에는 반드시 `--build` 플래그를 강제 적용하여 서비스를 기동한다.**
  ```bash
  docker compose up -d --build <수정된_서비스명>
  ```
* 빌드가 백그라운드로 성공적으로 완료되었는지 `docker compose ps`로 UP 상태를 검증하고 `docker compose logs -f`로 로그 스트림을 필터링한다.

### 4-2. 브라우저 도구 기동 배제 및 사용자 검증 의뢰
* WSL2 헤드리스 환경이므로 에이전트는 무리하게 가상 브라우저를 기동하지 않는다.
* 도커 컨테이너를 정상 구동 완료 상태로 안착시킨 후, 사용자가 웹 브라우저로 즉시 검증할 수 있는 로컬 링크 주소(예: `http://localhost:3000/`)와 메뉴 조작 동선, 그리고 검증해야 할 기대 결과(예: "일봉 백필 완료 시 steps 상세 결과의 수치 확인")를 친절하게 정리하여 사용자에게 정중히 테스트를 위임하고 피드백을 기다린다.
